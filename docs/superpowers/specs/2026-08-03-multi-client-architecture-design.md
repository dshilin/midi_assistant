# Мультитенантная архитектура: один агент — много клиентов

Дата: 2026-08-03. Статус: черновик.

## Цель

Один код, разворачиваемый для множества магазинов (клиентов). Все клиенты продают
напольные покрытия. У каждого клиента свой каталог, свои остатки и свой канал
общения (Telegram-бот и/или сайт). Добавление нового клиента не должно требовать
правки ядра.

## Принципы

- Агент не знает про поставщиков. Он читает только из БД конкретного клиента.
- Изоляция: у каждого клиента свой файл `clients/<slug>/products.db`.
- Скрейп и разбор данных — вне ядра, на этапе загрузки.
- Новый клиент заводится разработчиком вручную, без админки.

## Структура клиента

```
clients/
  midi/                  # текущий клиент, мигрируем как есть
    config.toml          # name, slug, bot_token, site_url
    catalog.csv|xlsx     # прайс-лист с шапкой (артикул, наименование, цена, ссылка)
    stock.xlsx           # остатки (выгрузка 1С)
    products.db          # каталог + спеки + остатки — только этот клиент
  <новый_клиент>/        # копия структуры, свой конфиг
    config.toml
    catalog.csv|xlsx
    stock.xlsx
```

Код никогда не хардкодит путь к БД: только через конфиг клиента. Клиент без
конфига или БД игнорируется.

## Каталог: единый входной формат — csv/xlsx с шапкой

Система принимает каталог как `catalog.csv` или `catalog.xlsx`; первая строка —
шапка. Колонки распознаются по названию шапки через алиасы, поэтому никакого
маппинга колонок в конфиге нет:

| Ожидание | Алиасы |
|----------|--------|
| артикул  | артикул, код, sku, article |
| наименование | наименование, название, name |
| цена     | цена, price, стоимость |
| ссылка   | ссылка, url (необязательно) |

Спеки (бренд, коллекция, модель, цвет и т.п.) в V1 заполняет GPT-разбор
названий. Прямой импорт доп. колонок из каталога отложен до клиента, которому
это реально нужно.

## Скрейп — вне системы

Общего скрейпера в ядре нет. Под сайт конкретного клиента один раз пишется
скрипт `clients/<slug>/scrape.py`, который сохраняет `catalog.csv`. Он не часть
ядра: его можно переписать или заменить. Если магазин сам выгружает прайс из
админки (Bitrix/1С) — скрейп вообще не нужен.

## Остатки

Остатки грузятся из `stock.xlsx`. Формат выгрузки 1С типовой; если у клиента
порядок колонок другой — одна строка маппинга в конфиге клиента.

## Загрузка клиента

`python -m app.ingest <slug>`:

1. читает `catalog.csv|xlsx` по именам шапки → `products` (пересборка);
2. читает `stock.xlsx` → `stock` (пересборка);
3. GPT-разбор названий в `floor_covering_specs` (общий и неизменный).

## Агент и каналы — только по клиенту

- `agent_fsm.py` принимает `client_slug`, через `db.py` открывает
  `clients/<slug>/products.db`.
  SQL-запросы поиска и расчёта не меняются.
- Telegram-бот: один процесс, токен берёт из конфига по slug, диалог роутится
  по slug, `client_slug` живёт в state.
- Сайт: эндпоинт `/{slug}` и `/chat`, существующий `static/chat.html`
  переиспользуется.

## Что откладываем (YAGNI)

- Веб-админку — клиенты заводятся руками.
- price_xlsx адаптер как отдельный код — не нужен, csv/xlsx вход покрывает.
- Расширение схемы facts: когда появится клиент с более богатыми свойствами —
  добавим колонки и обновим промпты разом для всех клиентов.
- Дедупликацию и сравнение поставщиков — у каждого клиента свой каталог.

## Тестирование

- тесты переносятся на временную БД клиента (tmp), не на глобальный products.db;
- тест загрузки: на вход csv/xlsx с шапкой → в БД клиента легли products/stock;
- тест роутинга по slug: запрос клиента А не видит данные клиента Б.
